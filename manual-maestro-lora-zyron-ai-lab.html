Propósito del manual#

Este Manual Maestro establece un sistema ordenado y reutilizable para planificar, preparar, entrenar, evaluar, documentar y publicar adaptadores LoRA dentro de ZYRON AI LAB. Su diseño es local-first: una vez instaladas las dependencias, los datos, configuraciones, registros y resultados pueden permanecer bajo control directo de ZYRON, sin depender de plataformas externas de entrenamiento, almacenamiento o seguimiento.

El contenido está escrito para personas con distintos niveles técnicos. Cada término se explicará antes de utilizarse y cada fase incluirá criterios de entrada, acciones, evidencias, listas de verificación y condiciones de aprobación.

Alcance inicial#

El programa comprende tres líneas de entrenamiento:

  1. LoRA de personaje: identidad visual y consistencia del robot ZYRON.
  2. LoRA de identidad personal: representación autorizada del rostro de Henry Izquierdo.
  3. LoRA de estilo: lenguaje visual corporativo de ZYRON.

Principios rectores#

  • Autonomía local: los activos permanecen bajo control de ZYRON.
  • Reproducibilidad: todo resultado debe poder repetirse desde su ficha de experimento.
  • Trazabilidad: cada LoRA se relaciona con versiones concretas del dataset y de la configuración.
  • Trabajo por etapas: ninguna fase se aprueba sin su evidencia y lista de verificación.
  • Privacidad y autorización: las imágenes personales requieren consentimiento, finalidad definida y almacenamiento controlado.
  • Calidad medible: la evaluación utiliza pruebas repetibles y comparaciones entre versiones.
  • Aprendizaje acumulativo: decisiones, problemas y mejoras se convierten en conocimiento reutilizable.

Flujo maestro#

Definir → Preparar entorno → Diseñar dataset → Depurar → Crear captions → Configurar → Entrenar → Evaluar → Corregir → Publicar → Documentar

Criterio general de finalización#

Un proyecto LoRA se considera terminado cuando posee dataset autorizado y versionado; captions revisados; palabra de activación documentada; configuración registrada; archivos de salida identificados; evaluación completada; limitaciones descritas; respaldo validado; ficha del modelo; registro de entrenamiento y notas de versión.

CAPÍTULO 1. PRESENTACIÓN DEL PROGRAMA ZYRON LoRA#

1.1 Identidad del programa#

El Programa de Entrenamiento LoRA de ZYRON AI LAB es un sistema institucional para desarrollar adaptaciones especializadas de modelos generativos de imágenes. No se limita a ejecutar entrenamientos: organiza todo el ciclo de trabajo, desde la definición del objetivo hasta la publicación de una versión evaluada, respaldada y documentada.

Su finalidad es que ZYRON pueda construir capacidades propias de entrenamiento, evitar la improvisación y conservar el conocimiento obtenido en cada experimento. El programa transforma actividades aisladas —reunir imágenes, redactar captions, ajustar parámetros o comparar resultados— en un proceso controlado con responsables, evidencias y criterios de aprobación.

1.2 Necesidad que atiende#

Un LoRA puede producir resultados visualmente atractivos y, aun así, ser difícil de repetir o utilizar. Esto ocurre cuando no existe control sobre el origen de las imágenes, las versiones del dataset, los parámetros, los prompts de evaluación o las decisiones tomadas durante el proceso.

El programa responde a cinco problemas frecuentes:

  1. datasets formados sin criterios uniformes;
  2. configuraciones modificadas sin registro;
  3. resultados evaluados únicamente por impresión personal;
  4. archivos guardados con nombres ambiguos;
  5. aprendizajes que se pierden al terminar el experimento.

ZYRON AI LAB abordará estos riesgos mediante un flujo único, plantillas normalizadas y puntos de control obligatorios.

1.3 Qué es un LoRA, explicado de forma sencilla#

Un modelo base ya sabe generar una gran variedad de imágenes. Entrenarlo nuevamente desde cero sería costoso y exigiría grandes cantidades de datos y capacidad de cómputo. Un LoRA aprende solamente una adaptación relativamente pequeña: por ejemplo, cómo representar con consistencia un personaje, un rostro autorizado o un estilo visual.

El resultado no sustituye al modelo base. Se utiliza junto con él y modifica su comportamiento según una intensidad ajustable. Por eso, un LoRA puede entenderse como una capa especializada de aprendizaje que se conecta al conocimiento general del modelo.

Esta solución ofrece cuatro ventajas para ZYRON:

  • archivos más pequeños que un modelo completo;
  • menor tiempo y demanda de entrenamiento;
  • posibilidad de mantener distintas especializaciones separadas;
  • facilidad para comparar, actualizar o retirar una versión.

Un LoRA no es una copia exacta garantizada ni corrige por sí solo un dataset deficiente. Su calidad depende de la selección de imágenes, los captions, la configuración, la evaluación y la compatibilidad con el modelo base.

1.5 Líneas iniciales de entrenamiento#

Línea A. Personaje robot ZYRON#

Busca reproducir de manera consistente su silueta, rostro, colores, materiales, proporciones y rasgos distintivos. Requiere imágenes variadas, pero fieles a una identidad visual única.

Línea B. Identidad personal de Henry Izquierdo#

Busca representar un rostro autorizado en diferentes encuadres, expresiones e iluminaciones sin perder identidad. Requiere protección reforzada de los archivos, consentimiento documentado y criterios estrictos contra resultados degradantes, engañosos o no autorizados.

Línea C. Estilo corporativo ZYRON#

Busca aprender una dirección artística: paleta, iluminación, atmósfera, composición, materiales y lenguaje futurista corporativo. No pretende memorizar una sola imagen ni introducir el logotipo como texto; busca una identidad visual generalizable.

1.8 Reglas operativas del programa#

  1. No se entrena con imágenes sin procedencia y autorización verificables.
  2. No se modifica un dataset aprobado sin crear una nueva versión.
  3. No se sobrescribe una configuración utilizada en un entrenamiento.
  4. No se publican resultados seleccionando únicamente los mejores ejemplos.
  5. No se declara éxito sin ejecutar la matriz de evaluación definida.
  6. No se elimina una versión fallida antes de registrar su causa y aprendizaje.
  7. No se emplea un LoRA de identidad personal fuera de su finalidad autorizada.

  • La línea del proyecto está identificada: personaje, identidad o estilo.

  • La procedencia y autorización de las imágenes pueden demostrarse.
  • Se definieron usos permitidos y usos prohibidos.

  • Se acordaron criterios preliminares de éxito.
  • Se creó la carpeta oficial del proyecto.
  • Se asignó un código único al proyecto.

Criterio de aprobación: todos los puntos deben estar completos o acompañados por una excepción escrita y aprobada.

CAPÍTULO 2. OBJETIVOS, ALCANCE Y PERFILES DE USUARIO#

2.1 Objetivo general#

Desarrollar en ZYRON AI LAB una capacidad autónoma, reproducible y documentada para crear adaptadores LoRA de personaje, identidad y estilo, mediante un flujo local controlado que proteja los datos, permita evaluar resultados objetivamente y convierta cada experimento en conocimiento reutilizable.

2.2 Objetivos específicos#

  1. Estandarizar la planificación de proyectos LoRA.
  2. Definir criterios verificables para crear y aprobar datasets.
  3. Normalizar captions, palabras de activación y metadatos.
  4. Registrar las configuraciones y condiciones de cada entrenamiento.
  5. Evaluar fidelidad, flexibilidad, calidad y sobreentrenamiento con pruebas comparables.

  7. Mantener versiones, respaldos y evidencias de cada proyecto.
  8. Desarrollar material formativo reutilizable en la Academia web de ZYRON.
  9. Reducir la repetición de errores mediante lecciones aprendidas.
  10. Facilitar la incorporación progresiva de nuevos operadores y evaluadores.

2.3 Alcance incluido#

El manual cubrirá:

  • preparación y validación de un entorno local;
  • organización de proyectos, rutas y nombres de archivos;
  • selección, autorización, depuración y versionado de imágenes;
  • creación y revisión de captions;
  • configuración y ejecución de entrenamientos;
  • monitoreo de archivos, registros y uso de recursos;
  • evaluación cualitativa y cuantitativa básica;
  • diagnóstico, corrección y reentrenamiento;
  • exportación, respaldo y publicación interna;
  • documentación técnica, operativa y formativa;
  • tres flujos específicos para las líneas iniciales de ZYRON.

2.4 Fuera de alcance#

Esta primera versión no pretende:

  • entrenar un modelo fundacional completo desde cero;
  • depender de plataformas externas como requisito del flujo;
  • convertir material sin autorización en datos de entrenamiento;
  • garantizar identidad perfecta en todas las poses, estilos o composiciones;
  • sustituir la revisión humana por una puntuación automática;
  • enseñar edición avanzada de imágenes o video;
  • autorizar usos comerciales, legales o comunicacionales no definidos;
  • publicar modelos personales o corporativos de forma automática.

CAPÍTULO 3. FUNDAMENTOS DE LoRA EXPLICADOS SIN TECNICISMOS INNECESARIOS#

3.1 La idea central#

Un modelo generativo de imágenes puede compararse con una persona que ya aprendió a dibujar miles de temas. Si ZYRON necesita que esa persona aprenda un personaje particular, un rostro autorizado o una estética corporativa, no es necesario enseñarle nuevamente todo lo que sabe. Se le proporciona una enseñanza adicional, pequeña y especializada.

Esa enseñanza adicional es el LoRA. Aprende cambios concretos y los guarda separados del modelo base. Cuando se desea utilizar la especialización, se carga el modelo base y se conecta el LoRA; cuando no se necesita, se desconecta.

3.2 Relación entre los componentes#

Componente Explicación sencilla Función
Modelo base El conocimiento general que ya sabe generar imágenes. Proporciona anatomía, objetos, iluminación, estilos y composición general.
Dataset El conjunto de ejemplos seleccionados para enseñar. Muestra el concepto, sus rasgos constantes y sus variaciones.
Caption La descripción escrita de cada imagen. Indica qué aparece y ayuda a separar el concepto del contexto.
Palabra de activación Término poco común asociado al concepto. Permite invocar la especialización en un prompt.
Configuración Las decisiones técnicas del entrenamiento. Controla cuánto, cómo y durante cuánto tiempo aprende.
LoRA El archivo pequeño que contiene la adaptación. Modifica temporalmente el comportamiento del modelo base.
Prompt de evaluación Instrucción repetible utilizada para probar. Permite comparar versiones bajo condiciones similares.

La calidad final no depende de un único componente. Un buen dataset con captions deficientes puede enseñar relaciones incorrectas; una configuración razonable no compensa imágenes contradictorias; una evaluación improvisada puede ocultar fallas importantes.

3.3 Cómo aprende un modelo de imágenes#

Durante el entrenamiento, el sistema recibe una imagen, su caption y una versión alterada de esa imagen. Intenta reconstruir la información visual de acuerdo con la descripción. Luego mide la diferencia entre lo esperado y lo obtenido, y ajusta gradualmente los parámetros entrenables del LoRA.

Este ciclo se repite muchas veces:

  1. leer un ejemplo y su caption;
  2. realizar una predicción;
  3. medir el error;
  4. calcular un pequeño ajuste;
  5. repetir con otros ejemplos;
  6. guardar puntos de control para evaluarlos.

La palabra error no significa que el entrenamiento haya fallado. Es una medida matemática que orienta el aprendizaje. Una pérdida menor puede ser positiva, pero no garantiza por sí sola una imagen mejor ni mayor capacidad de generalización.

3.4 Qué aprende realmente un LoRA#

Un LoRA aprende patrones repetidos en los datos. Por eso es fundamental decidir cuáles repeticiones son deseadas y cuáles son accidentales.

En un personaje#

Debe aprender identidad, proporciones, colores y rasgos distintivos. No debería aprender que el personaje siempre aparece en el mismo fondo, pose o encuadre.

En una identidad personal#

Debe aprender rasgos faciales y relaciones que preservan identidad. No debería asociar a la persona con una sola ropa, expresión, iluminación o edad aparente si esas condiciones no forman parte del objetivo.

En un estilo#

Debe aprender paleta, textura, iluminación, atmósfera y composición. No debería memorizar sujetos, textos, logotipos o escenas específicas que se repiten por accidente.

3.5 Entrenamiento e inferencia#

Son dos momentos distintos:

  • Entrenamiento: el LoRA aprende a partir del dataset. Consume más recursos, produce registros y genera archivos de salida.
  • Inferencia: el LoRA ya entrenado se utiliza para crear imágenes. Se combina con el modelo base, un prompt, una semilla y una intensidad.

Modificar la intensidad durante la inferencia no vuelve a entrenar el LoRA. Solamente cambia cuánto influye la adaptación sobre la imagen generada.

3.6 Compatibilidad con el modelo base#

Un LoRA se construye para una familia o arquitectura concreta. Aunque dos modelos generen imágenes, sus estructuras internas pueden ser incompatibles. Por eso la ficha del LoRA debe registrar:

  • familia y versión del modelo base;
  • resolución de trabajo prevista;
  • componentes entrenados;
  • formato del archivo;
  • condiciones bajo las cuales fue evaluado.

La similitud del nombre comercial no demuestra compatibilidad. ZYRON verificará siempre el modelo base exacto utilizado.

3.8 Rank y alpha sin fórmulas complicadas#

El rank determina cuánta capacidad tiene el LoRA para representar cambios. Un rank mayor puede capturar relaciones más complejas, pero no convierte automáticamente el resultado en uno mejor. Si el concepto es simple o el dataset es pequeño, una capacidad excesiva puede memorizar detalles no deseados.

El alpha ajusta la escala interna de esa capacidad. Para comparar experimentos, ZYRON registrará siempre rank y alpha juntos; nunca anotará uno sin el otro.

Nota técnica opcional#

La adaptación puede representarse de forma simplificada como:

Peso adaptado = Peso original + intensidad × escala × adaptación LoRA

En la formulación habitual, la adaptación se aproxima con dos matrices pequeñas. Esto permite aprender una modificación útil sin reentrenar todos los pesos del modelo.

La decisión no debe basarse solo en la curva de pérdida. Siempre se combinarán registros técnicos con pruebas visuales controladas.

3.10 Intensidad durante el uso#

La intensidad define cuánto influye el LoRA en la generación. Una intensidad baja puede conservar mayor libertad del modelo base; una intensidad alta puede reforzar identidad o estilo, pero también introducir rigidez y artefactos.

ZYRON evaluará varias intensidades con el mismo prompt y semilla. El rango recomendado se documentará en la ficha del modelo. No existe una intensidad universal válida para todos los modelos, LoRAs y prompts.

CAPÍTULO 4. GLOSARIO COMPLETO#

Este glosario utiliza definiciones operativas para ZYRON AI LAB. Cuando una herramienta muestre un término en inglés, se conservará entre paréntesis para facilitar su identificación.

A#

Adaptador#

Archivo o conjunto de pesos que modifica el comportamiento de un modelo base sin reemplazarlo. Un LoRA es un tipo de adaptador.

Alpha#

Valor que escala internamente la contribución del LoRA en relación con su rank. Debe registrarse junto con el rank.

Artefacto visual#

Defecto no deseado: deformaciones, texturas extrañas, duplicaciones, bordes rotos, manchas o detalles incoherentes.

B#

Batch o tamaño de lote#

Cantidad de ejemplos procesados antes de realizar una actualización. Un lote mayor suele consumir más memoria.

Bucket#

Grupo de imágenes con dimensiones o proporciones semejantes. Permite entrenar con distintos formatos reduciendo recortes o deformaciones innecesarias.

C#

Caption#

Descripción textual vinculada a una imagen del dataset. Ayuda al modelo a diferenciar el concepto principal de ropa, pose, fondo, iluminación y otros elementos.

Checkpoint#

Estado guardado del entrenamiento o modelo en un momento concreto. Permite evaluar versiones intermedias y retomar procesos cuando la configuración lo admite.

Concepto#

Aquello que el LoRA debe aprender: personaje, identidad, objeto, estilo u otra característica definida.

Configuración congelada#

Copia de los parámetros que se utilizarán en una ejecución. No se modifica después de iniciar; cualquier cambio crea una configuración nueva.

Curva de pérdida#

Representación del valor de loss a lo largo del entrenamiento. Ayuda a detectar inestabilidad, pero no determina por sí sola la calidad visual.

D#

Dataset#

Conjunto organizado de imágenes, captions y metadatos utilizados para entrenar o evaluar.

Dataset de validación#

Ejemplos o pruebas reservados para verificar generalización. No deben utilizarse de la misma manera que los datos de entrenamiento.

Dimensión o rank#

Capacidad interna asignada al LoRA para representar la adaptación. Más capacidad implica más recursos y no garantiza mejor resultado.

Dropout#

Técnica que omite aleatoriamente parte de la información entrenable para reducir dependencia excesiva de patrones concretos.

E#

Época (epoch)#

Una pasada completa por el dataset según las repeticiones y la configuración definida.

Entrenamiento#

Proceso mediante el cual el LoRA ajusta sus pesos usando imágenes, captions y una configuración.

Escalador de gradiente#

Mecanismo utilizado con ciertas precisiones numéricas para evitar valores demasiado pequeños o inestables durante los cálculos.

Evaluación ciega#

Comparación en la que la persona evaluadora no sabe qué versión produjo cada resultado. Reduce sesgos de preferencia.

F#

Fine-tuning o ajuste fino#

Adaptación de un modelo existente para una tarea o concepto. LoRA es una técnica eficiente de ajuste fino.

Formato seguro (safetensors)#

Formato de almacenamiento de pesos diseñado para evitar la ejecución de código incluida en archivos de modelos. Sigue siendo necesario verificar procedencia y compatibilidad.

G#

Generalización#

Capacidad de aplicar lo aprendido en poses, fondos, iluminaciones, encuadres o sujetos que no son copias del dataset.

GPU#

Procesador especializado en cálculos paralelos. Es el recurso principal para entrenamientos de imágenes viables en tiempo razonable.

Gradiente#

Información matemática que indica en qué dirección deben ajustarse los parámetros para reducir el error.

H#

Hiperparámetro#

Valor decidido antes o durante la configuración, como tasa de aprendizaje, rank, batch, resolución o número de pasos.

I#

Inferencia#

Uso de un modelo ya entrenado para generar resultados. No modifica el LoRA.

Intensidad o peso del LoRA#

Valor aplicado durante la inferencia para controlar cuánto influye la adaptación.

L#

Latente#

Representación comprimida en la que muchos modelos realizan parte de la generación. No es una imagen visible, aunque contiene información que luego se decodifica.

Learning rate o tasa de aprendizaje#

Tamaño de los ajustes realizados durante el entrenamiento. Es uno de los parámetros más sensibles.

Loss o pérdida#

Medida matemática de diferencia entre la predicción y el objetivo. Orienta el aprendizaje, pero no sustituye la evaluación visual.

LoRA#

Sigla de Low-Rank Adaptation. Técnica que aprende una adaptación mediante estructuras pequeñas en lugar de modificar todos los pesos del modelo.

M#

Matriz de evaluación#

Registro de prompts, semillas, intensidades, resultados, criterios y decisiones utilizado para comparar versiones.

Metadatos#

Información asociada a un archivo o experimento: origen, fecha, versión, parámetros, dimensiones, autorización o etiquetas.

Modelo base#

Modelo general sobre el cual se aplica o entrena la adaptación. Determina arquitectura, capacidades y compatibilidad.

Modelo fundacional#

Modelo entrenado con grandes volúmenes de datos para adquirir capacidades generales. Un LoRA no equivale a entrenar uno desde cero.

O#

Optimizador#

Algoritmo que utiliza los gradientes para actualizar los parámetros entrenables.

Overfitting o sobreentrenamiento#

Situación en la que el LoRA memoriza demasiado el dataset, pierde flexibilidad o reproduce relaciones accidentales.

P#

Palabra de activación (trigger word)#

Token o término distintivo utilizado para invocar el concepto aprendido. Debe ser estable, documentado y poco ambiguo.

Parámetro#

Valor interno que el sistema utiliza o aprende. En uso común también se emplea para referirse a opciones de configuración.

Paso de entrenamiento (step)#

Una actualización de los parámetros entrenables. El total de pasos depende del dataset, repeticiones, épocas y batch.

Peso#

Valor numérico interno de un modelo o intensidad aplicada a un componente. El contexto debe aclarar cuál significado se utiliza.

Precisión numérica#

Forma de representar números durante los cálculos. Afecta memoria, velocidad, compatibilidad y estabilidad.

Prompt#

Instrucción textual utilizada para generar una imagen. En evaluación debe registrarse exactamente.

Prompt negativo#

Instrucción que señala características que se desean evitar, cuando el flujo o modelo la admite.

R#

Rank#

Véase Dimensión o rank.

Regularización#

Conjunto de técnicas destinadas a reducir memorización y mejorar generalización, mediante datos, captions, dropout u otras decisiones.

Repeticiones#

Cantidad de veces que un grupo de imágenes se presenta adicionalmente dentro de una época o cálculo equivalente.

Reproducibilidad#

Capacidad de repetir una ejecución o evaluación con suficiente información para obtener un comportamiento comparable.

Resolución#

Dimensiones en píxeles utilizadas para procesar las imágenes. Influye en detalle, memoria y tiempo.

S#

Scheduler#

Regla que modifica la tasa de aprendizaje a lo largo del entrenamiento. No debe confundirse con el sampler de generación.

Seed o semilla#

Número que controla el punto inicial de un proceso aleatorio. Reutilizarla ayuda a comparar cambios bajo condiciones semejantes.

Sobreentrenamiento#

Véase Overfitting.

Subentrenamiento#

Aprendizaje insuficiente: el concepto aparece débil, inconsistente o poco sensible a la palabra de activación.

T#

Tasa de aprendizaje#

Véase Learning rate.

Texto codificado o text encoder#

Componente que transforma el prompt en una representación que el generador puede utilizar. Algunas configuraciones permiten entrenarlo parcial o totalmente.

Token#

Unidad en la que el codificador divide el texto. Una palabra puede convertirse en uno o varios tokens.

Trazabilidad#

Capacidad de relacionar objetivo, datos, configuración, ejecución, resultado, evaluación y decisión final.

Trigger word#

Véase Palabra de activación.

U#

Underfitting o subentrenamiento#

Véase Subentrenamiento.

V#

VAE o decodificador visual#

Componente que transforma representaciones latentes en imágenes visibles y, en algunos flujos, realiza el proceso inverso.

Validación#

Comprobación técnica o visual realizada antes de aprobar una etapa.

Versión#

Estado identificado y no ambiguo de un dataset, configuración, LoRA o documento.

VRAM#

Memoria disponible en la GPU. Limita resolución, batch, precisión y otros componentes que pueden cargarse simultáneamente.

CAPÍTULO 6. INSTALACIÓN Y VALIDACIÓN DEL ENTORNO EN WINDOWS#

6.1 Objetivo y criterio de aprobación#

El objetivo no es “instalar todo”, sino crear un entorno identificable, aislado y verificable. La instalación se aprueba cuando Git y Python responden, el entorno virtual puede recrearse, PyTorch informa el modo de cómputo correcto, la herramienta abre sin errores críticos y una prueba controlada produce evidencia.

El procedimiento se divide en dos rutas:

  1. Ruta ASUS P0: preparación local y validación en CPU, sin CUDA.
  2. Ruta NVIDIA P1–P3: entrenamiento con una GPU dedicada y PyTorch compatible con CUDA.

6.2 Preparación previa de Windows#

Antes de instalar:

  1. aplicar las actualizaciones estables de Windows y reiniciar;
  2. crear un punto de restauración cuando corresponda;
  3. comprobar fecha, hora y zona horaria;
  4. verificar al menos 30 GB libres después de las descargas previstas;
  5. crear una carpeta sin sincronización automática ni nombres ambiguos;
  6. confirmar que no se trabajará dentro de Descargas o del Escritorio temporal;
  7. registrar antivirus, proxy o políticas que puedan bloquear scripts;
  8. evitar ejecutar terminales como administrador salvo que un paso lo exija.

Ruta base recomendada:

C:\ZYRON_AI_LAB\lora\
├── repositorios\
├── entornos\
├── modelos\
├── datasets\
├── salidas\
├── logs\
└── respaldos\

6.3 Instalar y validar Git#

Git para Windows debe obtenerse desde su sitio oficial. La instalación puede realizarse mediante instalador o winget. Después se abre una terminal nueva y se ejecuta:

git --version
git config --global core.longpaths true

El primer comando debe mostrar una versión. El segundo ayuda con rutas extensas de repositorios. No se configurarán credenciales ni publicación remota si el proyecto no lo necesita.

6.4 Instalar la versión de Python compatible#

Python mantiene instrucciones oficiales para Windows y recomienda entornos virtuales por proyecto. Para sd-scripts, su documentación de Windows especifica Python 3.10.x como versión probada; versiones posteriores pueden funcionar, pero no deben adoptarse en producción sin validación.

Después de instalar Python se abre una terminal nueva:

python --version
python -m pip --version
python -m venv --help

Si existen varias versiones, se utilizará el selector instalado en el sistema para invocar explícitamente Python 3.10. La ficha de instalación registrará el ejecutable real:

where.exe python
python -c "import sys; print(sys.executable); print(sys.version)"

6.5 Crear un entorno virtual aislado#

Ejemplo para una instalación de prueba:

New-Item -ItemType Directory -Force C:\ZYRON_AI_LAB\lora\repositorios
Set-Location C:\ZYRON_AI_LAB\lora\repositorios
python -m venv venv-lora
.\venv-lora\Scripts\Activate.ps1
python -m pip install --upgrade pip

Si PowerShell bloquea la activación, no se recomienda reducir permanentemente la seguridad del sistema. Para una sesión controlada puede utilizarse una excepción limitada al proceso y luego cerrarse la terminal:

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
.\venv-lora\Scripts\Activate.ps1

Alternativamente se puede usar el activador .bat desde Símbolo del sistema. Toda excepción debe quedar documentada.

6.6 Ruta A — Validación del ASUS sin CUDA#

En el ASUS se instalará PyTorch para CPU únicamente con el comando vigente obtenido del selector oficial de PyTorch. No se copiará un comando CUDA, porque torch.cuda.is_available() debe permanecer en False en este hardware.

Prueba de identificación:

python -c "import torch; print('PyTorch:', torch.__version__); print('CUDA:', torch.cuda.is_available()); print('Dispositivo:', 'cuda' if torch.cuda.is_available() else 'cpu')"

Resultado esperado en el ASUS:

CUDA: False
Dispositivo: cpu

Esto no es un error. Confirma que el entorno de preparación local funciona sin atribuirle una GPU inexistente.

6.7 Ruta B — Validación de una estación NVIDIA#

Antes de instalar PyTorch CUDA:

nvidia-smi

El comando debe mostrar la GPU, controlador y memoria. Luego se seleccionará en el sitio oficial de PyTorch la combinación Windows, Pip, Python y CUDA compatible. No se fijará en el manual un comando universal porque las versiones soportadas cambian.

Después de instalar:

python -c "import torch; print(torch.__version__); print(torch.cuda.is_available()); print(torch.cuda.get_device_name(0) if torch.cuda.is_available() else 'SIN CUDA')"

La ruta NVIDIA se rechaza si:

  • nvidia-smi no funciona;
  • PyTorch informa CUDA: False;
  • el nombre de la GPU no coincide con la estación documentada;
  • se producen errores de controlador o bibliotecas;
  • la VRAM disponible no corresponde al perfil aprobado.

6.8 Instalar sd-scripts de forma reproducible#

La documentación oficial de sd-scripts debe revisarse antes de ejecutar comandos, porque las versiones mínimas de PyTorch y dependencias pueden cambiar.

Flujo controlado:

Set-Location C:\ZYRON_AI_LAB\lora\repositorios
git clone https://github.com/kohya-ss/sd-scripts.git
Set-Location .\sd-scripts
git rev-parse HEAD
python -m venv venv
.\venv\Scripts\Activate.ps1
python -m pip install --upgrade pip

Después se instala PyTorch según la ruta CPU o NVIDIA y, finalmente, las dependencias indicadas por la versión seleccionada de sd-scripts. El hash mostrado por git rev-parse HEAD se guarda en la ficha para poder reconstruir la instalación.

6.9 Alternativa con interfaz Kohya_ss#

Kohya_ss ofrece instalación local para Windows y puede simplificar la configuración visual. Su documentación actual distingue métodos uv y pip, y señala que la GPU NVIDIA es necesaria para entrenamiento en la ruta Windows documentada.

Política ZYRON:

  • usar sd-scripts directo cuando se requiera máxima trazabilidad de comandos;
  • usar Kohya_ss cuando la interfaz reduzca errores de configuración;
  • no mezclar dependencias de ambas instalaciones en el mismo entorno;
  • registrar repositorio, commit, método, Python y PyTorch;
  • probar primero con un proyecto mínimo sin datos sensibles.
